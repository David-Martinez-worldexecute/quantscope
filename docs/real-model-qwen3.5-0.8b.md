# Real model: Qwen3.5-0.8B, load time, forward latency and peak memory

This page records one engineering measurement, not a quality evaluation: can a 0.8B
multimodal checkpoint be loaded from disk and run one forward pass on this CPU-only
machine, and what does it cost in time and memory? Every number below comes from
`docs/evidence/qwen35_forward.json`.

## What was measured

- Model: `Qwen/Qwen3.5-0.8B`, revision `master`, two weight files (1,746,942,600 bytes
  safetensors + 50,900 byte index). Both SHA-256 digests were re-checked immediately
  before loading, so the numbers belong to those exact bytes and nothing else.
- Architecture, read from the same snapshot's `config.json`: `Qwen3_5ForConditionalGeneration`,
  24 text layers, of which 18 are gated DeltaNet (linear attention) and 6 are full attention,
  one full-attention layer every fourth position. Vision tower: 12 layers, patch 16,
  out width 1024.
- Environment: Python 3.12.10, torch 2.6.0+cu124, transformers 5.23.0, device `cpu`,
  dtype `bfloat16`. Two optional kernels were absent (`causal_conv1d`,
  `flash-linear-attention`), so the run used the reference PyTorch path — the latency
  below is an upper bound, not the fast path.
- Forward pass: prefill only, 64 random token ids, no generation loop, no KV-cache
  growth, three timed repeats.

## Results

| quantity | value |
| --- | --- |
| load (tokenizer + weights + dtype cast) | 95.64 s |
| peak working set, before load | 0.375 GiB |
| peak working set, after load | 3.417 GiB |
| peak working set, after forward | 3.488 GiB |
| forward, 64-token prefill (3 runs) | 0.6114 / 0.3062 / 0.3827 s |
| forward, median | 0.3827 s |
| logits shape | `[1, 64, 248320]`, all finite |

Parameter inventory: 2,214,531,200 bytes counted across every parameter tensor, of which
1,504,786,048 live in the text stack and 201,185,792 in the vision tower. The count is
larger than the unique storage because `tie_word_embeddings` is true, so the 248320×1024
embedding matrix is counted once under `embed_tokens` and once under `lm_head`; the
evidence file says so in `parameters.note` rather than hiding it.

Loading used `load_state_dict(..., assign=True)` over the loaded shards, which reported
1 missing and 15 unexpected keys — those are buffers the checkpoint does not store
(rotary frequencies and similar), computed by the model at construction time. The forward
pass succeeding with finite logits is the check that they were computed.

## What this does not show

- No accuracy, no perplexity, no comparison against any other weight format. Nothing here
  says the model is good at anything.
- CPU only: this is a host-memory number, not GPU peak memory or throughput.
- Prefill only: no token-by-token decoding, so no per-token latency and no KV-cache growth.
- Random token ids, not a natural prompt: the timing is a cost probe, not a quality probe.
- One revision, one machine, one dtype. A different snapshot would need its own record.

The evidence file carries the weight-file names, byte counts and SHA-256 digests, the
environment versions, the three timings, the memory samples and the limits above. It is
generated by re-reading the measurement and the download record and refusing to write if
either changed, so the page cannot drift away from the bytes it describes.
